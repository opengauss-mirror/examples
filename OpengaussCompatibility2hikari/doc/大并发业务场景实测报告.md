# 大并发业务场景实测报告

> 对应代码：OpengaussCompatibility2hikari/src/main/java/com/linyu/ospp/HighConcurrencyBusinessDemo.java
> 验证类：com.linyu.ospp.HighConcurrencyBusinessDemo

## 一、环境与做法

本机 openEuler-20.03 WSL 内运行 openGauss 7.0.0-RC3 与 dolphin（MySQL 协议），服务已启动。Windows 侧经 172.18.15.52:3306/mysql_db 访问，数据库用户为 mysqluser/openGauss@123。

新增独立验证类 HighConcurrencyBusinessDemo.java，模拟多用户并发下单业务。每个 worker 在单个事务内完成扣减自己账户余额、写入订单与提交，比单纯建连或单条 CRUD 更贴近真实业务。

连接池 maximumPoolSize 固定为 10，故意小于并发数，用于制造连接池竞争。worker 数取 50、100、200 三档。

运行方式如下，后两个参数分别传入 100 与 200 即对应其余档位：

```text
java ...HighConcurrencyBusinessDemo 172.18.15.52 50 mysql_db mysqluser openGauss@123
```

## 二、连接池与并发设计

| 设计点 | 取值与行为 |
| --- | --- |
| 连接池上限 | maximumPoolSize=10，固定且小于所有并发档位 |
| 每笔业务 | 单事务：UPDATE hc_accounts SET balance=balance-10，再 INSERT hc_orders，最后提交 |
| 并发竞争 | worker 数远超 10，超出连接请求阻塞排队，验证上限不被突破 |
| 一致性校验 | 订单数等于 worker 数，账户总余额等于初始 1000×N 减去扣减 10×N |

## 三、实测结果

实跑环境为 openGauss 7.0.0-RC3 与 dolphin。

| 并发 worker | 峰值活跃连接 | 成功与失败 | 总耗时 | QPS | 账户总余额校验 |
| --- | --- | --- | --- | --- | --- |
| 50 | 8，上限 10 | 50 / 0 | 351 ms | 142.5 | 49500，通过 |
| 100 | 10，上限 10 | 100 / 0 | 528 ms | 189.4 | 99000，通过 |
| 200 | 10，上限 10 | 200 / 0 | 845 ms | 236.7 | 198000，通过 |

## 四、一致性校验

控制台 [校验] 输出均为 PASS：

```text
[校验] 订单数=200 (期望=200) -> PASS
[校验] 账户总余额=198000 (期望=198000) -> PASS
```

订单数等于 worker 数，无丢失。账户总余额等于初始 1000×N 减去扣减 10×N，无超扣，无负余额。

## 五、结论

构建的是真实业务场景。每笔都是扣余额加写订单的事务，不是只建立连接。

超过最大连接数后再来连接，行为正确。200 并发争抢 10 个连接时，连接池被压满到 10 但从不突破上限，峰值活跃连接恒小于等于 maximumPoolSize，其余请求阻塞排队，全部成功提交，零失败。该结论与 verifyPoolLimit 一致，且压力更大。

高并发下数据一致。账户总余额与订单数完全符合预期，无并发写错乱。
