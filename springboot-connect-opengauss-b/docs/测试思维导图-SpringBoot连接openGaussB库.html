测试思维导图：Spring Boot + MySQL JDBC 连接 openGauss B 库（Issue #27）

37 个测试用例（BOM 默认 9.7.0 基线全通过）· 8 档驱动矩阵协议命令分三档 · FINDING A/B/D/F/G/H/I 已记录，6 个文档参数逐一实测

  • Spring Boot + MySQL JDBC × openGauss B 库 测试
    • 测试环境
      • openGauss 7.0.0-RC3（fe6f6e4b）B 库 proto_test_db / schema mysql_test_db
      • MySQL 协议端口 3308（enable_dolphin_proto = on）
      • Spring Boot 3.5.16 + JDK 17 + mysql-connector-j（BOM 默认 9.7.0）
    • 一、连接与认证（4 用例 ✓）
      • 正常连接；productName = MySQL，productVersion = 8.0.28-dophin-server
      • 错误密码 → 拒绝（failed in auth check）
      • 错误用户名 → 拒绝（no pg_hba.conf entry）
      • 连 5432 原生口 → 拒绝（Communications link failure）
      • FINDING A：getTables 报错 information_schema.TABLES 不存在（默认配置 dolphin.lower_case_table_names=0 下大小写敏感：小写可查；=1 并持久化后实测恢复）
    • 二、类型映射 + 6 个文档参数（8 用例 ✓）
      • 9 种类型往返：TINYINT / TINYINT(1)→Boolean / BIT(1)→Boolean / DECIMAL / DATE / DATETIME / TIMESTAMP / VARCHAR / BLOB（服务端将 TINYINT(1) 与 BIT(1) 均上报为 typeName=BIT）
      • tinyInt1isBit=false → Integer（参数生效）
      • transformedBitIsBoolean=false/true → getObject 均映射 Boolean（与官方文档备注一致）
      • useOldAliasMetadataBehavior ✓ 参数生效（原 FINDING C 改写为正向确认）：表列别名 true→getColumnName 返回别名 n、默认→原始列名 name；表达式别名两种设置均返回别名（符合文档备注）
      • useaffectedrows=true/默认：无变化 UPDATE 均返回 1（与文档备注「始终返回找到行数」一致）
      • allowMultiQueries=true → 两条语句两个结果集均返回（参数生效）；默认 → 服务端明确拒绝
      • FINDING B：零日期由 dolphin.sql_mode 的 no_zero_date 控制——默认写入被拒；去掉后可存储；存储后 zeroDateTimeBehavior 三档读取均生效（convertToNull→null / exception→抛错 / round→0001-01-01）
    • 三、DML 批量（3 用例 ✓）
      • PreparedStatement.addBatch 1000 行
      • JdbcTemplate.batchUpdate
      • rewriteBatchedStatements=true 提速约 17 倍（59ms vs 1020ms）
    • 四、事务（5 用例 ✓）
      • TransactionTemplate 提交可见 / 回滚不可见
      • 手动 Connection commit / rollback
      • SAVEPOINT 保存点 + 部分回滚
      • FINDING D：SERIALIZABLE 读回 4（REPEATABLE_READ）
    • 五、连接池（2 用例 ✓）
      • HikariCP maximumPoolSize=10 配置生效
      • CONNECTION_ID() 两次取连接同 id → 池复用确认
    • 六、已知限制专项（3 用例）
      • 游标：驱动层无报错、2000 行完整读回；协议层是否真游标待确认
      • Statement.setFetchSize(50) 无报错（可能被静默忽略）
      • 存储过程 CallableStatement 报错 information_schema.PARAMETERS 不存在（默认配置大小写敏感所致；lower_case_table_names=1 后大写可查）
    • 七、协议命令专项（9 用例 ✓，评审意见落地）
      • 7.1 COM_QUERY / 7.2 COM_INIT_DB / 7.3 COM_PING
      • 7.4 COM_STMT_PREPARE / COM_STMT_EXECUTE / COM_STMT_CLOSE（useServerPrepStmts=true 全生命周期）
      • 7.5 COM_STMT_SEND_LONG_DATA：无零字节 1MB 完整往返（MD5 一致，9.7.0 基线）
      • FINDING H：8.0.28~8.4.0 档读回仅 1040384 字节（= 127×8192，丢末块 8KB）；9.7.0/26.7.0 档完整
      • FINDING F：含 0x00 二进制被按 C 字符串截断为前缀（200 字节读回 150；客户端预编译路径无此问题）
      • 7.6 COM_STMT_RESET（clearParameters 后复用，8.0.33 及以上档正常）
      • FINDING I：8.0.28 档此序列直接崩溃 openGauss 服务端进程（EOFException 断连、可复现 3 次）
      • 7.7 COM_STMT_FETCH：驱动层可用、协议层待确认
      • 7.8 COM_SET_OPTION（allowMultiQueries 多语句）
      • FINDING G：多语句后续 SELECT 结果集 getMoreResults() 不可得（DML 均落库）
      • 7.9 COM_QUIT；无 JDBC 触发路径的命令在报告 4.1.8 说明
    • 驱动版本矩阵（8 档 × 37 用例）
      • 8.0.28（文档基准）：FINDING I 崩溃 + FINDING H 丢 8KB，其余 30 通过
      • 8.0.33 / 8.1.0 / 8.3.0 / 8.4.0：36/37（仅 FINDING H，RESET 正常、服务端不崩）
      • 9.7.0（Boot 默认）/ 26.7.0（最新）：37/37 全部通过
      • 三档行为：8.0.28 崩 / 8.0.33~8.4.0 丢数据 / 9.7.0+ 正常 → 基础功能与驱动版本无关，协议命令专项与驱动版本相关（缺陷在服务端）
    • 结论
      • Boot 3.x + 新驱动基础 CRUD / 事务 / 批量 / 类型映射 / 连接池可用
      • 服务端预编译 + SEND_LONG_DATA/RESET 场景建议 9.7.0 及以上驱动（FINDING H/I）
      • 支撑 docs 仓版本范围表述更新："8.0.28 及以上均可正常工作"
